# SEO Audit — 2026-04-01

**Run:** Full audit, suffix `-2` (see filename). Workspace: `RealEstatePortfolio`. Audit-only; no application code changes.

## Executive summary

- **Crawl signals are coherent:** `robots.ts` exposes a sitemap URL, blocks obvious app/API paths, and aligns with `proxy.ts` public routes; authenticated `(app)` shell uses layout-level `noindex`, matching intent for non-marketing URLs.
- **Indexable marketing URLs** use `getAppOrigin()` for stable absolute canonicals and mostly complete titles, descriptions, and Open Graph; JSON-LD in root layout (Organization / WebSite / WebApplication) plus FAQPage on public calculator routes is structurally sound and matched to visible FAQ copy.
- **Gaps:** In-app calculator routes under `/calculators/*` duplicate public `/tools/*` content without an explicit canonical to the public URL (mitigated by `noindex`); the home page embeds the marketing calculator via dynamic + client-only loading, so the interactive calculator body is thin in initial HTML. Production-only checks (Search Console, live HTTP) remain outstanding.
- **Recommendation:** Ship is strong for metadata and indexing strategy; schedule canonical consolidation for duplicate calculator surfaces and verify `NEXT_PUBLIC_APP_URL` on production deploys.

## Severity-ranked findings

### Critical

- None identified in repo review.

### High

- None identified; duplicate calculator URLs are `noindex` on the app side, limiting duplicate-index risk.

### Medium

- **In-app calculator URLs lack canonical to public equivalents** — Duplicate topical pages exist at `/calculators/brrr` (etc.) vs `/tools/brrr`; app pages set `robots: { index: false, follow: true }` but do not set `alternates.canonical` to the preferred `/tools/*` URLs (`app/app/(app)/calculators/brrr/page.tsx` and siblings). Impact: minor crawl consolidation; `noindex` already reduces indexing duplication.
- **Home page calculator preview is client-heavy** — `PublicCalculator` is dynamically imported with a loading placeholder and is a client component (`app/app/page.tsx`, `app/components/marketing/public-calculator.tsx`). Impact: primary marketing copy and H1 are server-rendered; the “Try the free calculator” block’s interactive value may be underrepresented in raw HTML vs JS-rendered output. Cross-lane: see Performance / mobile audits if LCP or content parity is a concern.

### Low

- **Default OG/Twitter image inheritance** — Many routes rely on root `layout.tsx` defaults for images; acceptable for brand consistency; tool-specific social images would be an enhancement only.
- **Operational dependency on `NEXT_PUBLIC_APP_URL`** — Wrong value in a given environment skews canonicals, sitemap, and robots sitemap URL (`app/lib/app-url.ts`). Not verifiable as “wrong” from static review alone.

## Risk & impact assessment

Unresolved **medium** items are unlikely to cause severe ranking loss given strong `noindex` on duplicates and solid public metadata. The largest real-world risk is **misconfigured site URL in production**, which would misalign canonicals and sitemap entries for all routes. Thin HTML for the home calculator block may modestly affect how much calculator-related copy is indexed from the homepage versus the dedicated calculator URL.

## Recommendations (prioritized)

1. **Confirm `NEXT_PUBLIC_APP_URL`** in production matches the live hostname (including `www` vs apex) so `metadataBase`, canonicals, `sitemap.xml`, and `robots.txt` sitemap directive stay aligned.
2. **Optionally add `alternates.canonical`** on `app/app/(app)/calculators/*/page.tsx` (and hub if needed) pointing to the matching `/tools/*` or `/investment-property-calculator` URLs to consolidate signals for crawlers that still fetch `noindex` pages.
3. **After deploy:** Submit sitemap in Search Console and spot-check URL Inspection for `/`, `/tools`, and one calculator URL.
