## Severity-ranked findings

### Critical

### High

- **Architecture / maintainability — files far above ~300-line guidance** — `docs/architecture-and-build-practices.md` §4.2 recommends considering splits past ~300 lines. Multiple production modules remain very large, increasing review burden and merge conflict risk.  
  **Evidence (line counts, this workspace):**  
  - `app/app/(app)/analyze/deal-analyzer-form.tsx` — **1389** lines  
  - `app/components/pricing-cards.tsx` — **511** lines  
  - (From prior same-day audit enumeration, also oversized: `add-property-wizard.tsx`, `property-form.tsx`, marketing calculators, `properties/page.tsx`.)

### Medium

- **Design compliance — heavy elevation on product chrome** — `docs/policies/design-spec.md` emphasizes clarity over decoration and warns against heavy shadows (see §1, §9 in spec). Onboarding and cookie surfaces use strong shadows.  
  **Evidence:** `app/app/(app)/onboarding-panel.tsx` — `shadow-2xl`, `shadow-lg shadow-accent/25`, `hover:-translate-y-px` on CTA (~96–132); `app/components/consent/cookie-consent-banner.tsx` — `shadow-lg` on fixed bottom bar (~23).

- **Design compliance — marketing imagery** — Large screenshots on landing/pricing use `shadow-lg` for depth. Acceptable for marketing; noted against spec preference for minimal chrome.  
  **Evidence:** `app/app/page.tsx` (~204); `app/app/pricing/page.tsx` (~117–135).

- **Efficiency — deal GET recomputes full portfolio summary** — Opening a saved deal triggers `buildPortfolioSummaryPayload(user)` (counts + `findMany` with mortgages + metrics) even though the deal row is already loaded — work grows with portfolio size and tier limits.  
  **Evidence:** `app/app/api/deals/[id]/route.ts` (~110–111); `app/lib/server/portfolio-summary-payload.ts` (`buildPortfolioSummaryPayload` / `loadPortfolioSummaryCore`).

- **Security (defense in depth) — property PATCH `where` clause** — After ownership is established, `update` could include `userId` in `where` to guard against future refactors that skip the pre-check (same observation as run 1).  
  **Evidence:** `app/app/api/properties/[id]/route.ts` (PATCH path after `getActiveAppUser` / `getPropertyForUser`).

- **Observability — account delete permanent** — Failures in Stripe cancel or Clerk delete are logged but not consistently elevated to Sentry compared with other API paths.  
  **Evidence:** `app/app/api/account/delete-permanent/route.ts` (Stripe/Clerk error branches).

### Low

- **Architecture — positive patterns verified** — `app/lib/server/portfolio-summary-payload.ts` loads properties with `include: { mortgages: true }` in one query (no N+1 loop detected in this module). `app/app/api/import/portfolio/route.ts` validates rows via `parseRow` and plan limits before writes.

- **Performance — `force-dynamic` placement** — `export const dynamic = "force-dynamic"` is scoped to `app/app/(app)/layout.tsx`, analyze, and admin — not the root layout — matching `docs/architecture-and-build-practices.md` §2.5. Root `app/app/layout.tsx` has no `force-dynamic`.

- **Performance — config and hints** — `app/next.config.ts` includes `experimental.optimizePackageImports: ["lucide-react", "recharts"]`. `app/app/layout.tsx` adds preconnect/dns-prefetch for RentCast, Clerk, Stripe, PostHog as configured (~118–137).

- **Security — public routes** — `app/proxy.ts` documents public paths including webhook, contact, CSP report, health; matches `docs/security/security-notes.md`. `app/app/api/account/restore/route.ts` correctly uses `getAppUser()` for restore flows.

- **Product mantra** — `app/app/global-error.tsx` uses semantic tokens (`bg-background`, `text-muted`, `bg-accent`) and reports to Sentry when DSN is set; aligns with thoughtful, on-brand failure UX.

- **Technical debt** — Targeted `eslint-disable` remains minimal (e.g. `theme-toggle.tsx`); no broad `any` usage surfaced in quick grep (English “any” in copy matches excluded).

## Risk & impact assessment

- **Unresolved High (large files):** Developer velocity and defect risk rise as single files own multiple concerns; user impact is indirect (bugs, slower fixes) until a bad edit ships.
- **Medium (deal GET payload, design chrome, observability gaps):** Deal GET cost affects perceived performance for power users with many properties. Shadow-heavy UI slightly diverges from brand minimalism. Missing Sentry on some delete paths could hide production incidents during account closure.
- **Likelihood:** Large-file pain is ongoing; deal GET cost scales with usage of saved deals + portfolio size; design issues are visible but not blocking.

---

## Recommendations (prioritized)

1. When editing `deal-analyzer-form.tsx`, `pricing-cards.tsx`, or add-property flows, **extract subcomponents or hooks** in the same PR to begin shrinking file size without a big-bang refactor.
2. For `GET /api/deals/[id]`, **evaluate a lighter `portfolioContext`** (narrower query or cached slice) if monitoring shows latency or DB time concentrated here.
3. **Align fixed overlays** (onboarding modal, cookie banner) with design-spec elevation guidance — reduce shadow depth or replace with border/subtle bg where product agrees.
4. **Harden `PATCH /api/properties/[id]`** with `userId` in the Prisma `where` clause; **add Sentry** to permanent-delete failure branches for parity with other critical APIs.
