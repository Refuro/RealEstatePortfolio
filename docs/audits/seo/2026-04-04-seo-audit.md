### High

#### H1 — Homepage `CALCULATOR_LINKS` contains three broken paths (404s)

**Location:** `app/app/page.tsx` lines 141–146, rendered at lines 392–401.

**Evidence:**
```
const CALCULATOR_LINKS = [
  { label: "Deal analyzer", href: "/investment-property-calculator" },  // ✓ correct
  { label: "BRRRR calculator", href: "/brrrr-calculator" },             // ✗ no route
  { label: "Fix and flip calculator", href: "/fix-and-flip-calculator"},// ✗ no route
  { label: "STR vs LTR calculator", href: "/str-ltr-calculator" },      // ✗ no route
];
```

The correct canonical paths (confirmed from page.tsx files) are:
- `/tools/brrr` (`app/app/tools/brrr/page.tsx`)
- `/tools/fix-and-flip` (`app/app/tools/fix-and-flip/page.tsx`)
- `/tools/str-vs-ltr` (`app/app/tools/str-vs-ltr/page.tsx`)

No Next.js redirects exist in `next.config.ts` for these legacy paths.
`app/.agents/product-marketing-context.md` lines 151–153 also references these stale paths as "top-of-funnel assets," which may cause future automation or agent instructions to repeat the error.

**Impact:**
1. Users clicking these links from the homepage will hit 404 pages, breaking the homepage→calculator funnel.
2. Google may discover and attempt to crawl these 404 URLs via homepage link signals, creating crawl noise with no payoff.
3. Internal PageRank flow from the home page (the highest-priority page in the sitemap, `priority: 1`) is wasted on dead destinations rather than the intended calculator pages.

**Fix:** Update `CALCULATOR_LINKS` in `app/app/page.tsx` to the correct paths. Update `.agents/product-marketing-context.md` to correct URLs as a secondary step.

#### M4 — Programmatic state calculator pages (~200 URLs): thin content risk as footprint scales

**Location:** `app/app/tools/[calculator]/[location]/page.tsx`; `app/lib/marketing/calculator-location-pages.ts`.

**Evidence:** 4 calculator slugs × 50 US states = 200 URLs. State-specific differentiation comes from: unique meta titles/descriptions (`buildLocationMetaDescription`), merged FAQs (`mergeLocationFaqs`), breadcrumb, and the state name injected into H1/headings. **Impact:** Low immediate risk (differentiation is adequate for state-level long-tail intent). Risk rises if state-specific FAQs or content depth are not added over time, as pages become more similar to each other. Mitigated by canonical pointing each state page to itself (not to the national page).

**Monitor:** Track Search Console impressions/index coverage for `/tools/*/*` — flag if significant pages fall into "Crawled but not indexed."

#### M5 — `sitemap.ts` uses `lastModified: new Date()` for all entries

**Location:** `app/app/sitemap.ts` — every entry uses `lastModified: new Date()`.

**Evidence:** Every sitemap entry dynamically reports "today" as the last modified date on every request. This means Google sees all 223 URLs as "changed today" on every crawl — including static legal pages (`priority: 0.3`, `changeFrequency: "yearly"`).

**Impact:** Crawlers rely on `lastModified` signals to prioritize recrawl frequency. Reporting every URL as "today" degrades the signal quality and may increase crawl budget usage on low-value pages. For the 200 state pages (programmatic, rarely changed), this misrepresents actual freshness.

**Fix options:**
1. Use a static date for content that doesn't change frequently (e.g. `new Date("2026-04-01")` for legal pages).
2. Source `lastModified` from a content version constant or last-deployed timestamp for the programmatic pages.
3. Minimum: set accurate static dates for `/privacy`, `/terms`, `/changelog` based on actual last-modified content dates.
